Три участника, три зоны по ролям продукта: **Пользователь (1)**, **Организация (2)**, **Админ и основа (3)**. Имена: 1 — ____, 2 — ____, 3 — ____.
Отмечайте выполненное `[x]` в своём PR. Зоны и ветки — в [OWNERSHIP.md](OWNERSHIP.md), сущности, статусы и правила — в [DATA_MODEL.md](DATA_MODEL.md) (читать обязательно до начала работы).

## 1. Пользователь

- [ ] 1.1. Справочник видов спорта: модель `Sport`, стартовый список, «свой вариант» при создании события (нормализация и защита от дублей по правилам из DATA_MODEL).
- [ ] 1.2. Модель и API `Event`: создание, чтение, редактирование автором. Поля и валидации по DATA_MODEL.
- [ ] 1.3. Создание мероприятия пользователем (форма: спорт из списка или свой, время, место, условия, режим записи, уровень, лимит мест).
- [ ] 1.4. Лента и поиск: текст, фильтры (спорт, дата, режим записи, уровень), сортировка по ближайшим. Выдаётся только `published`.
- [ ] 1.5. Карточка мероприятия: всё из DATA_MODEL, организатор со ссылкой, участники по правилам видимости, состояние моей записи, заглушка «Публикация недоступна» для снятых событий.
- [ ] 1.6. Запись в двух режимах с проверкой правил на сервере: `free` → `confirmed`, `request` → `pending`; отмена; повторная запись; запреты (своё событие, снято, прошло, нет мест).
- [ ] 1.7. «Мои мероприятия»: где я записан (со статусами и подписями) и что организую.
- [ ] 1.8. Обсуждение под событием: вопрос от любого пользователя, ответы, плашка роли автора, скрытое сообщение показывается заглушкой. Подключить модерацию из админки (п. 3.6).
- [ ] 1.9. Профиль пользователя и публичный профиль автора события.

## 2. Организация

- [ ] 2.1. Модель и API `Organization`: создание профиля, подача и повторная подача заявки, статусы, причина отказа.
- [ ] 2.2. Экран подачи заявки: название, деятельность, спортивные интересы, контакты, описание.
- [ ] 2.3. Кабинет организации: статус заявки (подпись и цвет по DATA_MODEL), причина отказа, правка и повторная отправка.
- [ ] 2.4. До допуска: запрет публикации событий и скрытая публичная страница (проверка на сервере).
- [ ] 2.5. Публичная страница организации: описание, интересы, её события. Видна только `approved`.
- [ ] 2.6. Публикация события от имени организации: использует форму и API события из 1.2–1.3, добавляет выбор организатора. Событие публикуется сразу.
- [ ] 2.7. **Панель организатора** (общая): список участников, входящие заявки, принять и отклонить, результат виден участнику, управление своим событием. Работает и для пользователя-организатора, и для организации.
- [ ] 2.8. Киллер-фича (см. [KILLER_FEATURE.md](KILLER_FEATURE.md)): модель, серверная логика, экраны, связка с лентой и карточкой. Начинать после согласования идеи с командой.

## 3. Админ и основа

**Первыми в очереди (блокируют остальных):**
- [ ] 3.1. Каркас проекта: структура, запуск одной командой, БД и миграции, общий API-клиент, роутинг, раскладка страниц.
- [ ] 3.2. Вход-имитация: экраны входа и регистрации, демо-аккаунты трёх ролей, быстрое переключение, сессия, проверка роли на сервере. Модель `User`.
- [ ] 3.3. Дизайн-система и макет: цвета, шрифты (≥16px), контраст, кнопки, формы, карточки, бейджи статусов (подписи из DATA_MODEL), пустые и ошибочные состояния, адаптив mobile/desktop, понятность для старшего поколения.

**Админка и модерация:**
- [ ] 3.4. Админка, организации: список и поиск, просмотр сведений, одобрить, отклонить с обязательной причиной; решение отображается организации. Запись в `AuditLog`.
- [ ] 3.5. Админка, мероприятия: поиск, просмотр, переход к организатору и обсуждению; снять с публикации и удалить с обязательной причиной. Снятое нельзя найти в ленте и нельзя записаться, в том числе по ссылке.
- [ ] 3.6. Модерация обсуждений: скрыть или удалить отдельное сообщение, остальное остаётся.

**Данные и сдача:**
- [ ] 3.7. Демо-данные (сид): пользователи, организация до и после допуска, ≥5 видов спорта, события обоих режимов, заявки для рассмотрения, комментарии. Команда сброса и пересоздания. Список аккаунтов — в [DEMO_DATA.md](DEMO_DATA.md).
- [ ] 3.8. Деплой: прототип доступен экспертам по сети.
- [ ] 3.9. README.md: продукт, стек, структура, запуск, демо-доступы, сценарии, правила доступа и модерации, имитации, ограничения.
- [ ] 3.10. Презентация и сценарий показа; зеркало кода на GitVerse.
- [ ] 3.11. Финальная сквозная проверка шести сценариев на задеплоенной версии.

## Порядок работы

1. **Старт.** Участник 3 делает 3.1, 3.2 и минимум 3.3 и вливает в `main`. Участники 1 и 2 в это время читают DATA_MODEL, пишут контракт в `docs/api.md` (каждый — свои эндпоинты) и работают на моках.
2. **Основной этап.** 1.1–1.6, 2.1–2.5, 3.4, 3.7. Зоны идут параллельно.
3. **Стыки.** 1.8 + 3.6 (обсуждение и модерация), 2.6 + 2.7 (публикация и панель), 3.5 + 1.6 (снятие событий и запрет записи).
4. **Финал.** 2.8, полировка интерфейса, 3.8–3.11. Новые функции не добавлять.

## Сквозная проверка (сценарии ТЗ)

| № | Сценарий | Задачи | Ответственный за проверку |
| --- | --- | --- | --- |
| 1 | Пользователь создаёт событие (в т.ч. с новым видом спорта), другой находит и открывает | 1.1–1.5 | 1 |
| 2 | Организация подаёт заявку → админ одобряет или отклоняет → организация публикует событие | 2.1–2.6, 3.4 | 2 |
| 3 | Свободное присоединение: `confirmed`, организатор видит участника | 1.6, 2.7 | 1 |
| 4 | Заявка: `pending` → принята и отклонена, видно обеим сторонам | 1.6, 2.7 | 2 |
| 5 | Вопрос и ответ организатора, авторство различимо | 1.8 | 1 |
| 6 | Админ снимает событие: нет в ленте, записаться нельзя даже по ссылке | 3.5, 1.6, 1.5 | 3 |
