# Задачи и распределение

Три участника — A, B, C. У каждого свой срез продукта «от БД до экрана» (вертикаль), чтобы не ждать друг друга на стыках. Подставьте имена: A — ____, B — ____, C — ____.
Отмечайте выполненное `[x]` в своём PR. Детали зон и веток — в [OWNERSHIP.md](OWNERSHIP.md).

## Состояния (единые для всех, правим только вместе)

| Сущность | Статусы |
| --- | --- |
| Организация | `pending` (на рассмотрении) → `approved` / `rejected` (с причиной) |
| Мероприятие | `published` / `unpublished` (снято админом, с причиной) / `deleted` |
| Запись | `confirmed` / `pending` (ждёт решения) / `rejected` / `cancelled` |
| Режим записи | `free` (свободное) / `request` (по заявке) |
| Комментарий | виден / скрыт модератором |

Права проверяются на сервере. Матрица доступа (кто что может) — в `docs/api.md`.

## A. «События и запись» — ядро пользовательского пути

- [ ] A1. Справочник видов спорта в БД: стартовый список + «свой вариант» при создании события создаёт новую запись без правки кода. Нормализация названий (регистр, пробелы, дубли).
- [ ] A2. Модель и API мероприятия: название, описание, спорт, организатор (пользователь или организация), дата и время, адрес/описание места, режим записи, условия (подготовка, инвентарь), статус.
- [ ] A3. Создание мероприятия пользователем; создание от имени организации (только если она `approved`).
- [ ] A4. Лента и поиск: текстовый поиск, фильтры (спорт, дата, режим записи, уровень), сортировка по ближайшим. Не показывать `unpublished` и `deleted`.
- [ ] A5. Карточка мероприятия: вся информация, организатор со ссылкой на профиль/страницу, список участников, текущее состояние записи пользователя.
- [ ] A6. Запись: свободное присоединение (сразу `confirmed`) и заявка (`pending`). Запрет повторной записи, запись на своё событие, запись на снятое событие, в том числе по прямой ссылке.
- [ ] A7. Панель организатора: участники, входящие заявки, принять/отклонить, отображение результата у участника. Отмена записи пользователем.
- [ ] A8. «Мои мероприятия»: где я записан (со статусами) и что организую.
- [ ] A9. Показ недоступной публикации: понятное сообщение организатору и записавшимся, если событие снято или удалено.

## B. «Организации, админка, обсуждения»

- [ ] B1. Профиль организации и заявка на допуск: название, деятельность, спортивные интересы, контакты, описание; статус заявки виден представителю.
- [ ] B2. До допуска: организация не публикует события и не имеет публичной страницы. После `rejected` видна причина.
- [ ] B3. Публичная страница организации: описание, интересы, список её событий.
- [ ] B4. Кабинет организации: состояние заявки, свои события, переход к управлению участниками (панель из A7).
- [ ] B5. Админка, организации: список и поиск, просмотр сведений, одобрить / отклонить с причиной.
- [ ] B6. Админка, мероприятия: поиск и просмотр, переход к организатору и обсуждению; снять с публикации / удалить с причиной (причина видна организатору).
- [ ] B7. Обсуждение под событием: любой пользователь задаёт вопрос, организатор отвечает; авторство различимо (роль «организатор» подсвечена). Для событий по заявке — решение об ограничении видимости записать в документации.
- [ ] B8. Модерация обсуждений: админ скрывает или удаляет отдельное сообщение, остальное остаётся.
- [ ] B9. Профиль пользователя (демо-данные: имя, о себе, интересы), страница автора события.

## C. «Основа, киллер-фича, сдача»

- [ ] C1. Каркас проекта: структура, запуск одной командой, БД и миграции, общий API-клиент, роутинг. **Первый приоритет: нужен остальным в первые часы.**

- [ ] C4. Демо-данные (сид): пользователи, организация до допуска и после, ≥5 видов спорта, события обоих режимов, заявки на рассмотрение, комментарии. Команда сброса и пересоздания.

- [ ] C7. README.md: продукт, стек, структура, запуск, демо-доступы; описание сценариев, правил доступа и модерации, имитаций, ограничений.
- [ ] C8. Презентация и сценарий демонстрации; зеркало кода на GitVerse.

## Порядок работы (без дат, по фазам)

1. **Фаза 0 (первые часы).** C делает каркас (C1, C2, C3-минимум) и вливает в `main`. A и B пишут контракт в `docs/api.md` и `docs/DATA_MODEL.md` и работают на моках. Контракт сначала в отдельном маленьком PR.
2. **Фаза 1.** A1–A6, B1–B6, C4. Вертикали идут параллельно.
3. **Фаза 2.** A7–A9, B7–B9, начало C5. Интеграция: A и B проверяют стыки (создание организацией, комментарии на карточке).
4. **Фаза 3.** C5 до конца, UI-полировка, C6–C9. Новые функции не добавлять, только исправления.

## Сквозная проверка (сценарии ТЗ)

| № | Сценарий | Кто отвечает | Нужные задачи |
| --- | --- | --- | --- |
| 1 | Пользователь создаёт событие, в т.ч. с новым видом спорта; другой пользователь находит и открывает его | A | A1–A5 |
| 2 | Организация подаёт заявку → админ одобряет/отклоняет → организация публикует событие без повторного согласования | B | B1–B6, A3 |
| 3 | Свободное присоединение: сразу `confirmed`, организатор видит участника | A | A6, A7 |
| 4 | Заявка: `pending` → принята и отклонена, видно у обеих сторон | A | A6, A7 |
| 5 | Вопрос в обсуждении и ответ организатора, авторство различимо | B | B7 |
| 6 | Админ снимает событие: пропадает из выдачи, записаться нельзя даже по ссылке | B, A | B6, A6, A9 |
