## 1. Пользователь

- [x] 1.1. Справочник видов спорта: модель `Sport`, стартовый список, «свой вариант» при создании события (нормализация и защита от дублей по правилам из DATA_MODEL).
- [x] 1.2. Модель и API `Event`: создание, чтение, редактирование автором. Поля и валидации по DATA_MODEL. Для аккаунта `organization` — `organization_id` по задаче 2.6.
- [x] 1.3. Создание мероприятия пользователем (форма: спорт из списка или свой, время, место, условия, режим записи, уровень, лимит мест). Место выбирается компонентом карты из 2.9.
- [x] 1.4. Лента и поиск: текст, фильтры (спорт, дата, режим записи, уровень), сортировка по ближайшим. Выдаётся только `published`.
- [x] 1.5. Карточка мероприятия: всё из DATA_MODEL, организатор со ссылкой, участники по правилам видимости, состояние моей записи, заглушка «Публикация недоступна» для снятых событий.
- [x] 1.6. Запись в двух режимах с проверкой правил на сервере: `free` → `confirmed`, `request` → `pending`; отмена; повторная запись; запреты (своё событие, снято, прошло, нет мест). Сервис «принять / отклонить заявку» для панели организатора (2.7): решает только автор события, только из `pending`, с учётом лимита мест.
- [x] 1.7. «Мои мероприятия»: где я записан (со статусами и подписями) и что организую.
- [x] 1.8. Обсуждение под событием: вопрос от любого пользователя, ответы, плашка роли автора, скрытое сообщение показывается заглушкой. Подключить модерацию из админки (п. 3.6).
- [x] 1.9. Профиль пользователя и публичный профиль автора события.
- [x] 1.10. Подключить «Место встречи» в свои экраны: карточка площадки с контактом в карточке события (1.5), переключатель «Список / Карта» в ленте (1.4), поля `venue_id`, `lat`, `lng` в API события (1.2).

## 2. Организация

- [x] 2.1. Модель и API `Organization`: создание профиля, подача и повторная подача заявки, статусы, причина отказа.
- [x] 2.2. Экран подачи заявки: название, деятельность, спортивные интересы, контакты, описание.
- [x] 2.3. Кабинет организации: статус заявки (подпись и цвет по DATA_MODEL), причина отказа, правка и повторная отправка.
- [x] 2.4. До допуска: запрет публикации событий и скрытая публичная страница (проверка на сервере).
- [x] 2.5. Публичная страница организации: описание, интересы, её события. Видна только `approved`.
- [x] 2.6. Публикация события от имени организации. Аккаунт `organization` создаёт события только от имени своей организации, поэтому выбора организатора в форме нет: API события (1.2) сам ставит `organization_id` и вызывает функцию проверки из модуля `organizations` (представитель, статус `approved`). Участник 2 пишет эту функцию и отвечает за сценарий 2 целиком: событие публикуется сразу и видно на странице организации.
- [x] 2.7. **Панель организатора** (общая): список участников, входящие заявки, принять и отклонить через сервис модуля `registrations` (1.6), результат виден участнику, управление своим событием. Работает и для пользователя-организатора, и для организации.

**Киллер-фича «Место встречи»** ([KILLER_FEATURE.md](KILLER_FEATURE.md)):
- [x] 2.8. Модель и API `Venue` и `SportVenueType`: список с фильтрами (тип, вид спорта, область карты), получение по id. Подсказка типов площадок для вида спорта.
- [x] 2.9. Компонент `MapPicker`: выбор площадки на карте или своей точки, подсветка подходящих виду спорта, показ карточки с контактом. Leaflet + OpenStreetMap, атрибуция обязательна. При недоступной карте — запасной режим с текстовым адресом.
- [x] 2.10. Компонент и страница `EventsMap`: события на карте с фильтрами, краткая карточка по клику, вид для мобильных.
- [x] 2.11. Карточка площадки (контактное лицо, телефон, часы работы, как договориться) — общий компонент для формы, карточки события и карты.

## 3. Админ и основа

**Первыми в очереди (блокируют остальных):**
- [x] 3.1. Каркас проекта по [STACK.md](STACK.md) (монорепозиторий `apps/web`, `apps/api`, `packages/shared`, `docker-compose.yml` с Postgres, `.env.example`, команды `db:push`, `db:seed`, `dev`): структура, запуск одной командой, БД и миграции, общий API-клиент, роутинг, раскладка страниц.
- [x] 3.2. Регистрация и вход (настоящие, email + пароль): экраны регистрации (выбор типа аккаунта: участник или организация) и входа, `POST /auth/register`, `POST /auth/login`, `POST /auth/logout`, `GET /auth/me`; хэш Argon2id, сессия в cookie (`HttpOnly`, `SameSite=Lax`) и таблица `Session`; ограничение частоты попыток входа; проверка роли на сервере (middleware). Админ регистрацией не создаётся. **Демо-аккаунты остаются:** на экране входа кнопки «Войти как участник / организация / админ» входят в реальные аккаунты из сида. Модели `User` и `Session`.
- [x] 3.3. Дизайн-система `shared/ui` из утверждённого дизайна ([design/README.md](design/README.md), `tokens.css`, `home.html`); шрифты через `@fontsource`, а не Google Fonts. Состав: цвета, шрифты (≥16px), контраст, кнопки, формы, карточки, бейджи статусов (подписи из DATA_MODEL), метки и иконки типов площадок и видов спорта, стиль карты и карточки площадки (см. [DESIGN_BRIEF.md](DESIGN_BRIEF.md)), пустые и ошибочные состояния, адаптив mobile/desktop, понятность для старшего поколения.

**Админка и модерация:**
- [x] 3.4. Админка, организации: список и поиск, просмотр сведений, одобрить, отклонить с обязательной причиной; решение отображается организации. Запись в `AuditLog`.
- [x] 3.5. Админка, мероприятия: поиск, просмотр, переход к организатору и обсуждению; снять с публикации и удалить с обязательной причиной. Снятое нельзя найти в ленте и нельзя записаться, в том числе по ссылке.
- [x] 3.6. Модерация обсуждений: скрыть или удалить отдельное сообщение, остальное остаётся.

## Порядок работы

Готовые стартовые промпты и порядок запуска — в [START_PROMPTS.md](START_PROMPTS.md).

1. **Старт.** Участник 3 делает 3.1, 3.2 (сначала вход с демо-аккаунтами, затем регистрация) и минимум 3.3 и вливает в `main`. Участники 1 и 2 в это время читают DATA_MODEL, пишут контракт в `docs/api.md` (каждый — свои эндпоинты) и работают на моках.
2. **Основной этап.** 1.1–1.6, 2.1–2.5, 2.8, 3.4, 3.7. Зоны идут параллельно.
3. **Стыки.** 2.9–2.11 + 1.3, 1.5, 1.10 (карта в форме, карточке и ленте), 1.8 + 3.6 (обсуждение и модерация), 2.6 + 2.7 (публикация и панель), 3.5 + 1.6 (снятие событий и запрет записи).
4. **Финал.** Полировка интерфейса, 3.8–3.11. Новые функции не добавлять.
