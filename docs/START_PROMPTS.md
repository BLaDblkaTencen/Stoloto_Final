# Старт работы: порядок и промпты для Claude

Каждый участник работает на своём ПК со своим Claude Code. Здесь: что сделать до старта, порядок, и готовый промпт для каждой роли.

## 0. Один раз перед стартом (капитан)

Замёржить три PR **в таком порядке** (конфликтов между ними нет):
1. `chore/claude-workflow`: правила, задачи, модель данных, стек, ТЗ.
2. `chore/docs-design-system`: дизайн «Вместе» (`docs/design/`). Он ссылается на файлы из первого PR.
3. `feature/core-db-schema`: готовая схема базы данных (`apps/api/src/db/schema`, [DB_SCHEMA.md](DB_SCHEMA.md)) и уточнённый `DATA_MODEL.md`. Все таблицы создаются один раз здесь, участники их не пишут заново.

После этого все остальные работают только от свежего `main`.

## 1. Подготовка на каждом ПК

1. Установить: Node.js LTS (`winget install OpenJS.NodeJS.LTS`, затем `corepack enable`), Docker Desktop (или PostgreSQL), Git. Подробности — [STACK.md](STACK.md).
2. Клонировать репозиторий и взять свежий `main`:
   ```
   git clone https://github.com/BLaDblkaTencen/Stoloto_Final.git
   cd Stoloto_Final
   git switch main && git pull
   ```
3. Создать свою ветку (название ниже) и открыть в этой папке Claude Code.
4. Вставить промпт своей роли.

> Скрипт `scripts_worktrees.sh` нужен только если несколько Claude работают на **одном** ПК. Если у каждого свой ПК, он не нужен.

## 2. Порядок работы

1. **Первым стартует участник 3:** его каркас (3.1) и вход с демо-аккаунтами (3.2) блокируют остальных. Цель: первый PR с каркасом в течение 1–2 часов.
2. **Участники 1 и 2 в это время** читают документы, пишут контракт своих эндпоинтов в `docs/api.md` (маленьким PR), а экраны делают на моках. Схема БД уже готова, её не переписывают. Когда каркас в `main`, переходят на реальный API.
3. Любой общий файл (`docs/api.md`, `DATA_MODEL.md`, `packages/shared`, `shared/ui`) меняется отдельным маленьким PR.
4. PR открываются в `main`, мёржит капитан. Коммиты и PR на русском, в повелительном наклонении.

## 3. Общее начало каждого промпта

Вставляется перед текстом роли.

```
Ты работаешь над хакатонским прототипом «Платформа совместных спортивных активностей» (кейс Столото) в команде из трёх человек. У тебя своя зона, чужие модули не трогай.

Прочитай по порядку: CLAUDE.md, docs/TZ.md, docs/STACK.md, docs/DATA_MODEL.md, docs/DB_SCHEMA.md, docs/TASKS.md, docs/OWNERSHIP.md, docs/KILLER_FEATURE.md, docs/DESIGN_BRIEF.md, docs/design/README.md. Открой docs/design/home.html в браузере и изучи docs/design/tokens.css. Процесс работы — CONTRIBUTING.md: в main не пушим, только PR, ветки feature/…, коммиты на русском.

Главные принципы: модель данных и статусы — только из DATA_MODEL.md; все таблицы уже есть в apps/api/src/db/schema (описание — docs/DB_SCHEMA.md), заново их не создавай; права проверяются на сервере; стиль — только токены из tokens.css, любой текст ≥16px, элементы ≥48px, состояние не только цветом; всё ПО бесплатное; основной сценарий ТЗ не должен зависеть от карты. Если нужна правка в чужом модуле или общем контракте — запись в docs/REQUESTS.md, а не самовольная правка. Мелкими коммитами, перед PR: git fetch && git rebase origin/main.

Перед началом кратко перескажи, что понял про свою зону, и предложи план первого PR.
```

## 4. Участник 3: «Админ и основа»

Ветка: `feature/core-skeleton`.

```
Ты участник 3, зона «Админ и основа» (docs/OWNERSHIP.md). Твои задачи — раздел 3 в docs/TASKS.md. Первый приоритет, он блокирует остальных:

1. Задача 3.1, каркас по docs/STACK.md: pnpm-монорепозиторий apps/web (React + Vite + TypeScript + Tailwind v4 + React Router + TanStack Query), apps/api (Fastify + Zod + Drizzle + PostgreSQL), packages/shared; docker-compose.yml с Postgres; .env.example; команды pnpm dev, db:push, db:seed. Схема БД уже лежит в apps/api/src/db/schema (docs/DB_SCHEMA.md): подключи её в drizzle.config.ts и db:push как есть, таблицы заново не пиши. Один маленький PR как можно быстрее, чтобы остальные могли начать.

4. Дальше: 3.7 сид (≥5 видов спорта, ≥12 площадок в Красноярске — центр 56.0100, 92.8530; список площадок — docs/DEMO_VENUES.md, события обоих режимов, организации до и после допуска, заявки), затем админка 3.4–3.6.

Первый шаг: предложи структуру каталогов и список эндпоинтов /auth, затем строй каркас.
```

## 5. Участник 1: «Пользователь»

Ветка: `feature/user-sports-events`.

```
Ты участник 1, зона «Пользователь» (docs/OWNERSHIP.md). Твои задачи — раздел 1 в docs/TASKS.md. Ты владеешь моделями Sport, Event, Registration, Comment.

Пока участник 3 не влил каркас, не создавай проект заново. Сделай:
1. В docs/api.md (отдельным маленьким PR) опиши эндпоинты своей зоны: виды спорта, мероприятия (список с фильтрами и поиском, карточка, создание, редактирование), запись (оба режима, отмена), комментарии. Ошибки и права — по DATA_MODEL.md, включая запрет записи на снятое событие по прямой ссылке.
2. Таблицы твоих моделей уже есть: apps/api/src/db/schema/sports.ts, events.ts, registrations.ts, comments.ts (описание — docs/DB_SCHEMA.md). Не создавай их заново. Если своей таблице нужно изменение — маленький PR в свой файл схемы, и поправь сид. Схемы Zod для packages/shared — как только каркас появится в main.
3. Экраны делай по docs/design/home.html: главная с лентой, фильтрами и «Мои записи»; затем карточка события, форма создания, «Мои мероприятия». До каркаса — на моках в своей папке.
4. Стыки с участником 2, их нельзя пропустить:
   - Событие от имени организации (сценарий 2 ТЗ). Аккаунт с ролью organization создаёт события только от имени своей организации. API создания события ставит organization_id сам, а право публиковать проверяет функцией модуля organizations, которую пишет участник 2 (представитель и статус approved). Статус организации сам не проверяй. В форме для такого аккаунта показывай «Организатор: <название>» вместо выбора.
   - Решение по заявке. В модуле registrations сделай сервис «принять / отклонить заявку»: решает только автор события, только из pending, принятие учитывает лимит мест (та же транзакция с блокировкой строки события). Панель организатора участника 2 вызывает этот сервис; своих запросов к registrations у неё не будет. Сервис опиши в docs/api.md вместе со своими эндпоинтами.

Порядок: 1.1 справочник видов спорта (свой вариант без правки кода, нормализация по DATA_MODEL), 1.2 API события (сразу с organization_id по п. 4), 1.4 лента, 1.5 карточка, 1.6 запись в двух режимах (транзакция и блокировка строки события) вместе с сервисом решения заявки по п. 4, затем 1.3, 1.7–1.9, интеграция карты 1.10 после участника 2.

Первый шаг: предложи список эндпоинтов и схему первого PR.
```

## 6. Участник 2: «Организация»

Ветка: `feature/org-organizations`.

```

1. В docs/api.md (отдельным маленьким PR) опиши эндпоинты: организация (создание, подача и повторная подача заявки, статусы, причина отказа), публичная страница, площадки (Venue, SportVenueType) с фильтрами по типу, виду спорта и области карты (bbox).
2. Таблицы твоих моделей уже есть: apps/api/src/db/schema/organizations.ts и venues.ts (в нём и SportVenueType; описание — docs/DB_SCHEMA.md). Не создавай их заново. Если своей таблице нужно изменение — маленький PR в свой файл схемы, и поправь сид. Схемы Zod — когда появится каркас.

Город демо-данных — Красноярск, центр 56.0100, 92.8530; список площадок — docs/DEMO_VENUES.md.

Первый шаг: предложи список эндпоинтов и план первого PR.
```
